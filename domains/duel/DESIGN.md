# MiniDuel —— 两个小人对打 + 数据采集

比方块+三叉戟那套简单得多，只做一件事：**两个火柴人在地面上对打，打完记下每一帧**。
没有物理引擎依赖，纯 numpy；物理只有位置和速度，不做约束求解——所以不会像火柴人那次一样崩。

## 一、跑起来

```bash
cd D:\code\_mini_duel

# 1) 看对打：双击 duel_replay.html（6 局回放，可切换、可暂停、0.5×）
# 2) 采数据：
python collect_duel.py --episodes 800 --out duel.csv
# 3) 自检规则（200 局）：
python verify.py
# 4) 从 CSV 反算校验（不看内部状态，只查数据是否守规则）：
python inspect_duel.py
# 5) 重新生成回放：
python make_replay.py
# 6) 没有浏览器时的渲染自检（Node + canvas 桩）：
node test_render.js duel_replay.html
```

## 二、规则

两人各 100 血，场地 ±4m，60 帧/秒，一局最多 30 秒。

| 动作 | 前摇 | 活帧 | 后摇 | 射程 | 伤害 | 单次总帧 |
|---|---:|---:|---:|---:|---:|---:|
| 拳 | 6 | 3 | 9 | 1.15 m | 7 | 18（0.30s） |
| 踢 | 11 | 3 | 16 | 1.50 m | 11 | 30（0.50s） |
| 格挡 | — | — | — | — | 只吃 28% | 持续 |
| 受击硬直 | — | — | — | — | — | 10 帧 |

- **拳快近，踢慢远重**。贴身时拳的每秒伤害更高（23.3 vs 22.0），远距离只能用踢。
- 出招期间不能取消、不能格挡——**后摇是真实惩罚**，抓后摇是核心博弈。
- **招式平衡的真实改动只有两条**：拳程 1.05→1.15、bot 偏好距离域 0.80~1.75→0.75~1.45。
  改完踢的占比从 49.8% 降到 34.6%（拳 26.9%），次数比 拳 56% : 踢 44%。
  > 这里要记一笔：原计划还有"踢前摇 11→13、后摇 16→18、射程 1.5→1.35"，
  > 但那次批量替换的**字符串没对上，静默没执行**，而当时我把它当成生效了。
  > 分布确实变好了，但功劳全在上面两条。现在 `duel.py` 里踢还是最初那套（11/3/16/1.50/11），
  > **已采的 duel.csv 和新分片用的是同一套规则**——这一点比"数值更好看"重要，所以不回改。

## 三、数据

`duel.csv`（41MB）+ `duel_meta.json`（逐局结局与 bot 参数）。

每帧一行，**字段自解释，不靠记编码表**：

| 列 | 含义 |
|---|---|
| `ep` / `frame` | 第几局 / 第几帧 |
| `x0 x1` `vx0 vx1` | 位置(m) / 速度(m/s)，0=蓝方 1=红方 |
| `hp0 hp1` | 血量 0~100（2 位小数） |
| `st0 st1` | 状态：0闲置 1走 2出招 3格挡 4硬直 5倒地 |
| `tm0 tm1` | 当前状态还剩几帧 |
| `cd0 cd1` | 出招冷却还剩几帧 |
| `a0 a1` | 本帧下发的动作：0前进 1后退 2拳 3踢 4格挡 5待机 |
| `dist` | 两人间距（**积分之后**的观测值） |
| `atk` `mv` `vic` `blk` | 本帧出手方(-1无) / 招式(1拳 2踢 0无) / 被打方(-1无) / 是否被格挡 |
| `hdist` | **命中判定当时**的间距，-1=本帧无命中 |

`dist` 和 `hdist` 为什么两列：命中判定发生在物理积分**之前**，若用积分后的 `dist` 去校验射程，会出现"1.156m 打出 1.15m 的拳"这种假违规（我第一版就踩了，796 次）。数据要记**判定时用的那个值**。

## 四、实测（本机，单核单进程）

| 项 | 值 |
|---|---|
| 规模 | **800 局 / 562,636 帧 / 41MB / 39.2 秒** |
| 速度 | 纯环境 **99,809 帧/秒**；含 bot 与写盘 **21,289 帧/秒** |
| 对局长度 | 中位 703 帧（11.7 秒），最短 371 帧，最长 1423 帧 |
| KO 率 | **800/800 = 100%**（没有拖到 30 秒超时的） |
| 命中 | 20,148 次，被格挡 7,677 次 = **38%** |
| 招式 | 拳 11,257 / 踢 8,891（56% : 44%） |

### 校验结果（`inspect_duel.py`，从 CSV 反算）

```
① 血量单调性   单帧最大回升 0.00e+00
② 射程违规     0 次（拳 1.15m / 踢 1.50m）
③ 伤害对账     CSV 反算 vs 采集记录，最大差额 2.84e-14
④ 位置越界     0 次（|x| ≤ 4.00）
✓ 规则与数据完全一致，没有一条违规
```

### 谁赢？（800 局，胜者 vs 败者参数均值）

| 参数 | 胜者 | 败者 | 差 |
|---|---:|---:|---:|
| 反应延迟 `react`（帧，越小越快） | **5.03** | 7.13 | **−2.10** |
| 偏好距离 `prefer_dist` | 1.137 | 1.045 | +0.09 |
| 攻击性 `aggression` | 0.570 | 0.489 | +0.08 |
| 格挡倾向 `guard_bias` | 0.481 | 0.421 | +0.06 |
| 踢的比例 `kick_bias` | 0.382 | 0.373 | +0.01 |
| 发呆比例 `idle_bias` | 0.172 | 0.168 | +0.00 |

按差距分箱看更清楚：

| 反应速度差 | 局数 | 更快者胜率 |
|---|---:|---:|
| 0~1 帧 | 152 | 59.9% |
| 2~3 帧 | 257 | 70.8% |
| **≥4 帧** | 307 | **90.2%** |

| 攻击性差 | 局数 | 更凶者胜率 |
|---|---:|---:|
| <0.1 | 189 | 52.4% |
| 0.1~0.3 | 306 | 57.5% |
| **>0.3** | 305 | **68.9%** |

**这个规则下，反应速度是第一变量，攻击性第二。** 踢多踢少、发不发呆基本等于抛硬币（51~53%）。

## 五、并行度：一次就跑一个

`collect_duel.py` 是 `for ep in range(episodes)` 的串行循环——1 进程、1 环境，一局接一局。

为什么不多开：**一局平均 703 帧 = 0.03 秒**，而 Python 起一个进程（import numpy）要 0.2 秒以上。**进程启动比一局对打还贵**。要多开只有在每进程批量跑上百局时才摊得平，而 800 局单核 39 秒，还没到值得多开的数据量级。

这台机器 12 核，单核用满 1/12。真要压到几百万帧以上再谈多进程。

## 六、没做的

- **没有神经网络**。对打用的是参数化状态机（`bot.py`），不是学出来的策略。数据采好了，训模型是下一步。
- **2D、单项运动**。没有跳跃、没有横向走位、没有地形。规则就这么点，好处是能一眼验证。
- **bot 不会学习**。每个 bot 从随机参数开始，打完就丢，局与局之间无记忆。

## 七、下一步（如果继续）

1. 用 56 万帧训一个隐空间前瞻器：输入 `(obs, action)` → 预测 k 帧后的 `(hp, dist, st)`，看它能不能替代真实环境做 rollout。
2. 把 `bot.py` 换成 CEM 在线规划，看能不能打赢固定参数的 bot——**这是唯一能证明模型真学到东西的判据**。
3. 加一个"抓后摇"的动作维度，让博弈深一层。

## 八、常驻后台管线 `stream_duel.py`（无窗口、一直跑）

`collect_duel.py` 是"跑固定局数、产一份数据集、退出"；`stream_duel.py` 是"不设终点、
按分片不断吐、永远在后台跑"。前者做实验，后者攒料。

```bash
# 默认：跑在 shards/，限速 1.2 局/秒，分片总量 3GB 封顶，一直跑
python stream_duel.py

# 想快、想限时、想换目录
python stream_duel.py --eps-per-sec 3 --max-hours 8 --out-dir shards
python stream_duel.py --eps-per-shard 300 --prune-keep-gb 5

# 收工：放一个 STOP 文件（下一片跑完就停，不会写坏分片）
echo > STOP

# 随时体检
python inspect_stream.py --dir shards --last 5
```

### 四条设计规矩（都是为了"能一直挂着"）

1. **无窗口**。纯 CPU 计算，不画任何东西，也不抢焦点。
2. **分片落盘 + 先写 `.part` 再改名**。进程被中途杀掉只丢当前片，已完成的片完好；
   重启自动接着下一片编号（`part-NNNNN.csv.gz`）。
3. **限速**。满速能跑到 **13~45 局/秒**，即 4.4GB/天，纯属浪费。默认 1.2 局/秒 ≈ **0.9GB/天**。
4. **数据会过期，覆盖账本不会**。分片总量超过 `--prune-keep-gb`（默认 3GB）就删最老的，
   但 `coverage.json` 里累计的覆盖统计（多少局、多少帧、每种打法人次、20 格覆盖矩阵）
   一直留着——**体积有上限，认知没有**。

### 和一次性采集的区别：故意把打法撑开

一次性采集全是 `Bot.random()`（人类合理区间）。常驻管线按权重混入刻意偏科的原型：

| 原型 | 权重 | 说明 |
|---|---:|---|
| `param` | 50% | 常规参数机器人，最像人 |
| `param_wide` | 20% | 参数域拉满：反应 1~20 帧、攻击性 0.05~0.98 |
| `rush` | 10% | 只会往前压，几乎不格挡 |
| `turtle` | 9% | 疯狂格挡，几乎不主动 |
| `kite` | 7% | 拉开距离打后手 |
| `flail` | 4% | 均匀随机动作（无策略基线） |

另外**起始间距随机 1.0~6.5m**（原来固定在 2.2m±15%），覆盖"贴脸开局"到"隔场开局"。

### 实测（本机，生产参数）

| 项 | 值 |
|---|---|
| 每片 | 300 局 / 240,176 行 / **2.7MB**（gzip，压缩比约 6.7:1） |
| 单片实际计算 | 23.1 秒（13 局/秒），其余时间在限速睡眠 |
| 数据速率 | **约 9.2 KB/局 → 1.2 局/秒 ≈ 0.9 GB/天** |
| 3GB 上限能装多少 | 约 1100 片 ≈ **33 万局 / 2.3 亿帧**，按 1.2 局/秒算约 3.2 天填满 |
| 断点续跑 | 已验证：重启从 00003 接着写，ep 编号连续、无重复 |

### 质检（`inspect_stream.py`，读 gz 分片反算）

```
血量单调回升      0.00e+00      场地越界  0 次
射程违规          0 次          伤害对账  2.84e-14
分片编号连续、ep 无重复
覆盖矩阵 20 格 → 空格数逐片下降
```

覆盖矩阵（行=反应延迟档，列=攻击性档）是这套管线的核心产出：**空格就是模型没见过的人**。
常驻跑的判据不是"跑了多少局"，是"20 格还剩几格是空的"。

## 九、0.32M 进手机：装得进、算得动吗

先把数字钉死：**FlatWorld 的 StateLeWM 是 320,631 个参数，即 0.32M，不是 0.3B**。
两者差三个数量级——0.3B 能进手机是奇迹，0.32M 是常规操作。这个区别决定了要不要做。

### 体积：不是问题

`phone_probe.py` 造了一个**参数量按目标配平**（321,704，误差 0.3%）的网络实测：

| 精度 | 权重占用 |
|---|---:|
| fp32 | **1.23 MB** |
| fp16 | 0.61 MB |
| int8 | 0.31 MB |

1.23MB 对手机 APK 是可以忽略的量级（一个中文字体包都比它大）。

### 算力：瓶颈不在模型，在 CEM 的 576 次前向

CEM 一次规划 = 种群 48 × 视野 6 × 迭代 2 = **576 次前向**。本机单线程实测：

| 跑法 | 576 次前向耗时 |
|---|---:|
| **批量一次算完** | **30.35 ms** |
| 逐条 for 循环 | 449.1 ms（**慢 15 倍**） |
| 单次前向（批量均摊） | 52.7 µs |

两条直接可用的结论：

1. **必须批量**。同样的算子、同样的模型，逐条算慢 15 倍——因为 0.32M 的算子在矩阵乘之外
   还有固定的调度开销，一条一条来全花在开销上。
2. **必须单线程**。这是 FlatWorld 那次已经量过的（8 线程比 1 线程慢 10 倍），机器人小模型同理。

**手机侧估算**（口径写在代码里，不装成实测）：中端手机单核 fp32 有效算力按本机的 1/2~1/4 折，
一次规划 **60~120 ms**。

- 60fps 实时对打（每 5 帧重规划一次 = 83ms 预算）：**刚好卡在边缘**，能跑但没有余量。
- 回合制 / 慢节奏 / 只看"如果这样打会怎样"的推演：**完全够用**，几十毫秒没人感觉得到。

### 所以手机版该做成什么

不建议照搬"60fps 实时对打"。真正适合落地的三档，按投入从低到高：

| 档 | 做什么 | 要训的模型 | 手机侧工作量 |
|---|---|---|---|
| A | **只采集不上模型**：手机端点两下产生对局，数据回传，PC 统一训 | 没有 | 几乎为零 |
| B | **离线解说/预测**：把当前局面 + 候选动作喂给模型，返回"3 秒后会怎样" | 前瞻器 | 一个 ONNX 推理 + 一个列表页 |
| C | **实时 AI 对手**：CEM 在线规划驱动 NPC | 前瞻器 + 价值函数 | 推理 + 规划循环 + 线程/功耗处理 |

先做 A 是稳的：**A 不依赖任何训练成果，且 A 产出的数据正是 B、C 的原料**。

### 技术选型（手机侧）

- 模型导出：`torch.onnx.export`，固定 shape（CEM 里形状是固定的，动态 shape 只会更慢）。
- 运行时：**ONNX Runtime Mobile**（`onnxruntime` 的 Flutter 绑定）或 **TFLite**（`tflite_flutter`）。
  ORT 对小模型批量友好，TFLite 生态更成熟；两者都能到几百 KB~几 MB 的运行时开销。
- 备选：**ncnn / MNN**（腾讯 MNN 在国产安卓上启动快、体积小），但 Dart 绑定要自己写 FFI。
- 量化优先级：**先 fp16，再考虑 int8**。int8 会把 0.31MB 的体积优势换来判断精度下降，
  在 1.23MB 根本不是问题的情况下，不值得先做。

### 和现有天网手机端的关系

手机端 `tianwang_app` 目前是**冻结状态**（2026-10-26 定的：早跑通了，别动）。加这个功能属于新需求，
按规矩先定范围再动手。真正要先想清楚的是**它和已有的 `LlmEngine`（手机自跑 LLM 那条线）什么关系**——
是两个独立推理器并存，还是共用一套推理调度。这个决定影响不小，值得单独聊一次再动代码。

### 局面覆盖：比"打法覆盖"更硬的一层（300 局实测发现两个偏斜）

`inspect_stream.py` 会顺带统计真正进模型的状态分布。第一片（300 局）跑出来的结果：

| 项 | 实测 | 判断 |
|---|---:|---|
| 间距 1.0~1.5 m | **56%** | 过于集中 |
| 间距 0.5~1.0 m | 22% | |
| 间距 > 2.0 m | **只有 4%** | 远距离样本太少 |
| 贴墙帧（\|x\|>3.5） | **24.5%** | 四分之一的帧在边界上 |
| 同帧对撞（双方都在出招） | 26.4% | 正常，说明博弈有来有回 |
| 双方同帧发呆 | 0.3% | 干净，几乎没有废帧 |
| 同帧双命中被挤掉 | 0 次 | 格式隐患实际没触发 |

两条结论，都是量出来才发现的：

1. **随机化开局距离没用**。`start_gap` 已经从固定 2.2m 放宽到 1.0~6.5m，但稳态分布仍然是贴身——
   因为 bot 的策略天然收敛到交战距离，两人往中间一凑就再也分不开了。
   为此加了 `coward` 原型（只逃不打，偏好距离 2.6~3.6m）。
2. **但这只能把"单局内"的 >2m 占比从 2% 抬到 7%，抬不动整体**。原因是两条：
   一是 `coward` 只占 5% 的对阵组合，撑不起整体分布；二是场地只有 8m 宽、双方速度相同——
   **想跑的人跑不掉，一定被逼到墙角**（这也是贴墙帧从 24.5% 涨到 29.0% 的原因）。
   600 局聚合后 >2m 仍然只有 2%，**这一项没有改善，如实记下**。
   要真正造出远距离动态，得给部分对局换更大的场地——那会让 CSV 多出一个"场地尺寸"字段，
   属于中途改数据结构，不做。**记录在案，等下一版规则时一起改。**

> 这条比"跑了多少局"重要：**常驻管线最容易骗自己的地方，就是局数涨得很快、分布一动不动。**
> 所以每跑一段就该看一眼间距直方图，而不是只看 `coverage.json` 里的累计局数。

## 十、自我博弈进化 `evolve.py`（v2：随机到底 + 自动升级）

### 为什么有 v2（主人的一句话点破了根子）

v1 只有 6 个状态机参数，33 代就把"贴身 + 见招就挡 + 只用拳"这个唯一最优解榨干了。
主人说：**"相当于这么快就进化到终点了，证明你的规则太简单了。你可以不断叠加难度，
每到一个阶段自动升级，随机给一方武器、随机落道具或陷阱、地图随机生成 —— 随机到底。
这样的数据才是不断最优解，本质上就是迭代算法。"**

所以 v2 不做"更好的规则"，而是做**会自己变难的规则**：

1. **基因扩到 9 维**：6 原参数 + 武器（徒手/长矛/盾/双刃/投枪，离散）+ 捡道具倾向 + 绕陷阱倾向。
2. **环境每代随机生成**（`World.make_template(gen)`，确定性、全代共享）：场地宽度、障碍墙、
   道具雨、陷阱、物理参数（摩擦/击退）按代变。武器是基因、环境是难度，两套随机互不干扰。
3. **自动升级（迭代算法的核心）**：监控 EMA，连续 10 代摸顶（振幅 < 0.008）就从难度池
   **随机抽一个未启用的维度启用**，强制重新进化。进化循环嵌套在环境生成循环里，最优解永远在动。

到这里为止，前面所有管线都是**随机撒点**；`evolve.py` 换了个问题：让 24 个选手互相打，
赢的留下生下一代，每代最强的几个再互相对打决出"当代之王"。跑久了能回答两件事：

1. **强度天花板在哪** —— 进化到某个点不再变强，说明摸到规则上限了；
2. **规则在奖励什么** —— 冠军的基因就是答案。如果冠军是"站在 3m 外不动"，那不是我训练失败，
   是**这套规则在奖励不作为**，该改的是 `duel.py`。

### 9 维基因

| 维 | 含义 | 域 |
|---|---|---|
| `weapon` | 武器（离散）：徒手/长矛/盾/双刃/投枪 | 0..4 |
| `aggr` | 攻击性 | 0.02~0.99 |
| `guard` | 格挡倾向 | 0.00~0.99 |
| `kick` | 踢招比例 | 0.00~0.95 |
| `dist` | 偏好交战距离 | 0.50~4.20 |
| `react` | 反应延迟（帧，越小越快） | 1~20 |
| `idle` | 发呆比例 | 0.00~0.65 |
| `loot` | 捡道具倾向 | 0.00~0.95 |
| `avoid` | 绕陷阱倾向 | 0.00~0.95 |

**武器是物理属性，不是硬编码的打法**：`duel.py` 里 `WEAPONS` 改的是攻击表、格挡倍率、速度倍率、
受击加成；Bot 不认武器，只认 `me.max_reach()` 和"够得到才出招"。这样进化出来的是**武器无关的
稳健策略**，而不是"遇到长矛怎么办"的特例。

### 跑起来

```bash
python evolve.py --out-dir evo --pop 24 --reps 2 --resume   # 一直跑，断点续跑
python read_evo.py --dir evo                               # 把日志读成结论
echo stop > STOP_EVO                                        # 当前代跑完就停
```

或者双击 `run_evo.bat` / `stop_evo.bat`。

### 七份日志，各管一件事

| 文件 | 谁看 | 装什么 |
|---|---|---|
| `evo/evolve.log` | 人眼 | 每代一小段：难度 Lv + 世界摘要 + 强度/局时/KO/冠军/漂移/流派/趋势/诊断 |
| `evo/gens.jsonl` | 程序 | 每代一行完整记录（全种群基因 + 逐个体战绩 + 难度 + 世界模板） |
| `evo/progress.tsv` | Excel | 一行一代，直接画曲线（含 9 个基因均值列） |
| `evo/champions.jsonl` | 审计 | 每个新冠军一行 |
| `evo/levels.jsonl` | 升级 | **每次自动升级记一行**（哪一代谢顶、启用了什么维度、当时 EMA） |
| `evo/best_now.json` | 手机 | **新冠军导出**，直接 `Bot(**params)` 复现，含武器与难度 |
| `evo/state.json` | 续跑 | 种群 / 代数 / Elo / 难度等级 / rng |

**为什么要有日志而不是盯窗口**：这进程没有窗口。更重要的是——即便有窗口，看画面也只能看出
"这两个人打起来了"，看不出"冠军的 guard 从 0.42 漂到 0.91"。日志是精确的，画面是模糊的。

### 难度自迭代：为什么 EMA 不能跨难度比

**但当自动升级触发、环境变难时，`best_fit` 会掉 —— 这是在爬新坡，不是退化。**
`read_evo.py` 的难度阶梯段会把每次升级单独列出来，并给结论补一句提醒，避免误读成"白跑了"。

升级触发条件（`try_upgrade`）：最近 10 代 `best_ema` 振幅 < 0.008（真的摸顶）→
从 7 个难度维度（武器/地图/墙/道具/陷阱/物理/强敌池）里**随机抽一个**启用。
武器维度启用时，还会给一半个体随机换武器，强制引入武器多样性；升级后临时提高移民比例（缓降回基线），
逼种群重新探索。每升一级，`levels.jsonl` 多一行：
`{"gen":14,"level":1,"enabled":["weapon"],"ema":0.696}`。

> 这正合主人说的"迭代算法"：**进化循环是内环，环境生成循环是外环**。
> 内环把当前规则榨干（EMA 摸顶）→ 外环随机加一维难度 → 内环重新榨 → 没有固定的最优解。

### 踩到的第一个坑：**评分在奖励不作为**

第一版给平局 0.5 分（"打平也有一半收益"），结果第 3 代就进化出了：

```
冠军  aggr 0.51  guard 0.86  kick 0.34  dist 2.47  react 2  idle 0.25
```

`dist=2.47` 意味着**它站在踢击射程（1.5m）之外，永远不进入交战距离**；`idle=0.25` 是四分之一时间发呆。
它赢了，因为它既打不到人、也不会挨打，时间到双方满血 → 平局 → 0.5 分。
同期的指标：**KO 率从 79% 掉到 22%，平局从 16% 冲到 78%**。

这就是"能赢"和"会打"的差别。改成分档计分：

| 结果 | 得分 |
|---|---|
| KO 取胜 | 1.0 |
| 时间到判胜（血多） | 0.5 |
| 平局 | 0.05 |
| 输 | 0 |

改完第一代就回来了：KO 99%、平局 1%、局时从 1108 帧降到 594 帧。

> **教训**：适应度函数里"平局给多少分"决定了整个进化方向。给 0.5 等于告诉选手
> "不打也有五成收益"，进化会老老实实把"不打"练到极致。**规则怎么写，它就学什么，一点不含糊。**

### 第二个坑：`best` 跌了，但种群其实在变强

跑到第 4~5 代：`best 1.225 → 1.086`（跌），`mean 0.580 → 0.637`（涨）。
第一反应是"退化了"，其实是**种群把最强的那个追平了** —— 头尾差距在收窄。

这两件事在指标上长得一样，方向完全相反：一个是爬坡，一个是收口。
所以日志里加了同质化判定：`mean 涨 >0.02 且 best 动 <0.005 且头尾差距收窄到 70% 以内` → 报警。

另一个同类误导：`Elo 榜首` 原本报的是冠军自己的 Elo，而新个体从 1200 起跳，
一个刚冒头的新冠军 Elo 比退役老将低，看着像倒退。现在分开报 `冠军 Elo` 和 `种群最高 Elo`。

### 撞墙分析：日志里最有用的那一段（v2 扩展到 9 维 + 武器分布 + 难度阶梯）

基因撞到边界 = **这一维在规则里没有约束了**，继续跑只是刷分。`read_evo.py` 现在还会单列
**武器分布**（最后一代每把武器多少人、冠军用什么）和**难度阶梯**（每次升级的记录）。
撞墙翻成的改法：

| 撞墙的基因 | 说明什么 | 该改哪里 |
|---|---|---|
| `react` 到底 1 | Bot 直接读 `opp.state == ATTACK` 就格挡，没有信息延迟；拳前摇 6 帧，react=2 就够反应 | 给格挡加 2~4 帧启动帧，把"反应快"和"赌对了"拆开 |
| `guard` 到顶 >0.85 | 格挡零代价：不掉血、不进硬直、不吃冷却 | 格挡吃 3~5% 伤害，或格挡后 4 帧不能反击 |
| `aggr` 到顶 >0.9 | 空挥不赔钱，出招的期望收益是正的 | 未命中加 8~12 帧额外硬直 |
| `dist` 收敛成一个点 | 距离这一段没有分层策略 | 给不同距离不同招式（近身拳快、中距踢远） |
| `weapon` 全徒手 | 武器维度未启用（难度还低），或进化发现徒手最优 | 等到自动升级解锁武器维度再看；若已解锁仍全徒手，说明武器系统没产生区分度 |

**这份表比"跑了多少局"有用**：它直接告诉我下一次该动 `duel.py` 的哪个常量。

### 防退化：名人堂 + 移民 + 自适应变异 + 强敌池

自博弈最容易死在两件事上，v2 沿用并加了强敌池：

1. **只跟自己人打** → 进化成"专门克制当前种群"，一出圈就废。
   用**名人堂**（最近 24 个冠军）跨代检验；难度启用「强敌池」时再补随机原型，制造非平稳对手。
2. **早熟收敛** → 24 个个体练成一个模子。
   每代塞 15% 随机新生个体（移民）；多样性低于 0.20 时变异系数从 1.0 提到 1.6，低于 0.12 提到 2.4。
   日志里的**流派分布**就是给这件事用的：`反击×9 中庸×7 铁壁×4 猛攻×3 游走×1` 说明还在探索，
   全是同一种就该动手了。

### 性能

| 改动 | 省在哪 |
|---|---|
| 用 `step_raw` 跳过观测构造 | `_obs()` 占 37%，Bot 一个观测都没读过，构造数组纯属浪费 |
| 起手计数挪进 `Duel._apply_action` | 原来每帧扫两个 Fighter，多花一倍 tottime |

一致性无损：40 局同种子对比 `step` 与 `step_raw` 的 winner 和帧数，**40/40 全对**。

生产参数（pop 24 / reps 2 / 24 头名堂）**一代约 18~20 秒、~1250 局**，单核 1/12 占用。
一小时约 180 代。v2 比 v1 每代贵一点（环境随机生成 + 武器/道具/陷阱的逐帧感知），
但绝对值仍是"挂着不心疼"的量级。

### 导出到手机：`best_now.json` 是终点

主人的最终目的：**让物理规则模拟器自我进化，把冠军喂给天网手机版**。
`evo/best_now.json` 每代刷新，结构就是手机侧 `Bot(**params)` 能直接吃的：

```json
{
  "gene": [0, 0.70, 0.45, 0.72, 1.42, 1, 0.21, 0.60, 0.32],
  "gene_names": ["weapon","aggr","guard","kick","dist","react","idle","loot","avoid"],
  "params": {"weapon":"polearm", "aggression":0.70, "guard_bias":0.45,
             "kick_bias":0.72, "prefer_dist":1.42, "react":1,
             "idle_bias":0.21, "loot_bias":0.60, "avoid_bias":0.32},
  "weapon": "polearm", "style": "猛攻",
  "fit": 0.737, "champ_round_winrate": 0.56, "elo": 1432,
  "difficulty": 2, "difficulty_dims": ["weapon","wall"],
  "note": "直接填进 bot.Bot(**params) 即可复现；gene 是同份参数的原始浮点，手机侧按需取。"
}
```

手机侧只需 `Bot(**best_now["params"])`。`params` 已含武器字符串；
`gene` 是同份参数的原始浮点，要做轻量 NN 蒸馏时直接吃 `gene` 即可。

### 真跑数据（v2 是常驻进程，没有"终点"）

和 v1 不同，v2 不该再看"多少代就收敛了"——**自动升级会反复把收敛打散**。
真正要看的是 `read_evo.py` 的难度阶梯段：`levels.jsonl` 里有多少次升级、每次在什么 EMA 触发、
当前爬到第几级。v1 那张"6 代收敛表"是旧规则下的结论（最优解 = 贴身+见招就挡），
v2 的目的恰恰是把这个结论变成"一直动的目标"。

v1 留下的数值结论仍然成立、作为基线参考：6 代内 KO 率 69%→98%、平局 23%→1%、局时 18.5s→10.4s，
三个最先收敛的维度是 `dist~0.97`（拳击射程内）、`guard~0.9`、`react 1`——
这套基础规则的博弈深度确实浅，所以才需要 v2 的随机难度把它撑深。
